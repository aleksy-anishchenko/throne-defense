# Выкладка и откат

## Сценарий

1. SSH-ключ загружает API только в `incoming`, а не в работающий каталог.
2. `after-upload` под общей блокировкой копирует загрузку в новый каталог `releases`.
3. `npm ci` выполняется в новом каталоге. Работающий процесс и его зависимости не меняются.
4. SQLite создаёт согласованный снимок базы через `VACUUM INTO`. Кандидат запускается на
   этой копии, на свободном loopback-порту. Проверяются readiness, метка и рейтинг.
5. Автоматическая выкладка допускает только неизменный набор миграций и ту же версию схемы.
   Изменения схемы требуют отдельного плана совместимости, резервирования и обновления.
6. pm2 переключает API на новый каталог. Здесь возможен короткий перерыв обслуживания.
   Если запуск, проверка или `pm2 save` не удались, запускается предыдущий каталог.
   База при откате не восстанавливается из снимка: новые результаты не затираются.
7. Только после успеха API публикуются ресурсы сайта, затем отдельным вызовом — HTML.
   Старые хешированные ресурсы сохраняются; автоматического удаления пока нет.

API и HTML не переключаются одной транзакцией. Старая вкладка после изменения баланса
получает прежний окончательный отказ; клиент, который новее API, получает временный отказ
с возможностью повтора. Долговременная очередь результатов между перезагрузками — отдельная задача.

## Однократная подготовка VPS

Старая конфигурация SSH разрешает загрузку прямо в работающий `app`. Поэтому переход
требует установки нового root-owned `deploy-command` **до первого запуска нового workflow**.
Workflow проверяет командой `deployment-ready`, что подготовка завершена, прежде чем загружать файлы.

Подготовка выполняется владельцем сервера в согласованное окно обслуживания:

1. Остановить автоматические и ручные выкладки.
2. Проверить внешний бэкап и восстановление. Сохранить нынешнюю конфигурацию pm2.
3. От пользователя `throne` создать `/srv/throne-defense/{incoming,releases,shared}`
   и файл `/srv/throne-defense/deploy.lock` с правами `600`.
   Скопировать весь нынешний `app`, включая установленные `node_modules`, в
   `releases/bootstrap`. Это предыдущий готовый релиз, а не повторная установка из сети.
4. Скопировать `app/apps/server/.env` в `shared/server.env`, права `600`.
   `DATABASE_PATH` должен быть абсолютным и указывать на существующую рабочую базу вне
   `app`, `incoming` и `releases`. `PORT` — постоянный порт nginx (по умолчанию 3000).
5. Положить строку `bootstrap` в `releases/bootstrap/deploy/server/release-id`.
   Установить новую `deploy/pm2/ecosystem.config.cjs` в постоянный каталог
   `/srv/throne-defense/bin/ecosystem.config.cjs`.
6. От `throne` выполнить:

   ```bash
   pm2 delete throne-api
   THRONE_RELEASE_DIR=/srv/throne-defense/releases/bootstrap \
   THRONE_ENV_FILE=/srv/throne-defense/shared/server.env \
     pm2 start /srv/throne-defense/bin/ecosystem.config.cjs
   curl --fail http://127.0.0.1:3000/api/leaderboard
   pm2 save
   ln -s /srv/throne-defense/releases/bootstrap /srv/throne-defense/current
   ```

   Если запуск не удался, вернуть прежнюю конфигурацию pm2 и `app`; подготовка не завершена.
   Для bootstrap допустимо отсутствие нового `/api/ready`: откат проверяет `/api/health`
   и реальный рейтинг. Для всех новых релизов обязательна точная метка readiness.

7. От root установить обновлённый `deploy/server/deploy-command.sh` как
   `/srv/throne-defense/bin/deploy-command`, владелец root, права `755`.
   Обновить nginx из репозитория, выполнить `nginx -t`, затем reload.
8. Проверить `deployment-ready` через ключ выкладки. После этого разрешить workflow.

Не выполнять эти команды вслепую: пути, пользователь, порт и действующая конфигурация
VPS должны быть сверены. Репозиторий сам не меняет root-owned конфигурацию сервера.

## Ручной откат API

Предыдущий успешный каталог сохраняется в ссылке `previous`. От пользователя `throne`:

```bash
bash /srv/throne-defense/incoming/deploy/server/after-upload.sh rollback
```

Откат допускается только при совпадающих миграциях и версии схемы; перед переключением
выполняется пробный запуск на копии базы. Каталоги релизов автоматически не удаляются.
Удалять можно только явно ненужные каталоги, исключая `current` и `previous`.

## Ресурсы сайта

`assets/` дополняется до публикации HTML, без `--delete`. Ошибки ресурсов получают
`Cache-Control: no-store`, успешные хешированные файлы — годовой `immutable`.
Для отката страницы можно повторно опубликовать `index.html` предыдущей сборки:
её ресурсы остаются на сервере. Размер каталога следует контролировать; политика
уборки ресурсов должна учитывать срок поддержки открытых страниц.
