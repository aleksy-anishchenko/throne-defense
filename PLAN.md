### R01. P1 — можно отправить выдуманный рекорд без игры

- [ ] Спроектировать и реализовать проверку происхождения и достоверности результата либо явно принять и обозначить недоверенный характер рейтинга.

**Код:** [проверка правдоподобия](apps/server/src/services/plausibility.ts#L22), [приём результата](apps/server/src/routes/runs.ts#L34), [верхняя граница счёта](packages/game/src/systems/waves.ts#L89), [отладочный доступ к состоянию](apps/web/src/main.ts#L27).

**Причина.** Сервер получает только имя, зал, счёт, число волн и версию. Проверка сравнивает присланный счёт с теоретическим максимумом, но само число волн тоже выбирает отправитель. Нет подтверждённого сервером начала партии, журнала действий или повтора симуляции. `BALANCE_VERSION` — публичное число, не подтверждение подлинности. Параметр `?debug` дополнительно упрощает изменение состояния через `window.__throne`, но его удаление не закроет прямую отправку HTTP-запросов.

**Воспроизведено.** В чистой базе `POST /api/runs` с `playerName: "Review"`, `levelId: "throne-hall"`, `score: 4178290`, `wavesCleared: 100`, `balanceVersion: 9` возвращает **200**, `{ "rank": 1, "playerCount": 1 }`. Ни один игровой шаг перед запросом не выполнялся. Счёт взят из публичной `maxPossibleScore(level, 100)`.

**Последствия.** Любой посетитель может занять верх рейтинга; ограничение 10 отправок в минуту этому не мешает. Старые поддельные записи останутся в общем рейтинге и после смены баланса. Риск уже признан в коде и прежнем плане, но обход подтверждён конкретным примером.

**Как исправлять.** Для доверенного рейтинга выдавать идентификатор партии на сервере и проверять журнал допустимых действий детерминированной симуляцией с ограничениями по размеру и времени обработки. Идентификатор сам по себе не доказывает честный счёт. Если это пока слишком дорого, разделить проверенные и непроверенные результаты и определить порядок удаления накрутки. Не помещать «секрет подписи» в браузерный JS: игрок сможет его извлечь.

**Критерий готовности.** Запрос без подтверждённой партии не получает статус проверенного рекорда; изменённые счёт, зал и журнал отклоняются; обычная и бесконечная партия проходят проверку; устаревшие версии обрабатываются по явно выбранному правилу.

### R02. P1 — имя используется как идентификатор без подтверждения владельца

- [ ] Отделить идентификатор игрока от отображаемого имени и определить политику переименования.

**Код:** [схема результата](packages/contracts/src/runs.ts#L7), [группировка по имени](apps/server/src/services/leaderboard.ts#L32), [отправка после смены имени](apps/web/src/stores/game.ts#L232), [таблица runs](apps/server/src/db/migrations/001-runs.sql#L7).

**Причина.** Все записи одного `player_name` считаются одним игроком, а любой клиент может отправить это имя. Нормализация Unicode и ограничения длины проверяют текст, но не принадлежность имени. Токена игрока или иной идентификации нет.

**Сценарий.** Два независимых клиента отправляют результат под одним именем: второй результат изменяет лучший результат общей строки первого. Обратная проблема уже проверяется текущим e2e как допустимое поведение: «Сменить имя» повторно публикует ту же партию, и в таблице становится двое. Повторяя смену имени, один человек может занять все строки.

**Последствия.** Подмена чужого рекорда, смешивание результатов одноимённых людей, неверное число игроков и заполнение топа копиями одной партии. Проверка честности счёта из R01 сама по себе эту проблему не решает.

**Как исправлять.** Ввести `player_id`, привязанный к серверной сессии или выбранной системе входа; имя оставить отображаемым атрибутом. Если допустимы только гостевые профили, явно определить ограничения восстановления и защиту от массового создания. При переименовании менять профиль, а не создавать ещё одного участника с копией результата. Старые имена автоматически считать подтверждёнными владельцами нельзя.

**Критерий готовности.** Чужая сессия не может изменить запись существующего игрока; одинаковые отображаемые имена не смешивают личности; переименование не увеличивает число игроков и не копирует партию.

### R03. P2 — повторная отправка создаёт дубликаты, база растёт без границы

- [ ] Добавить идемпотентность отправки и правила хранения истории партий.

**Код:** [безусловный INSERT](apps/server/src/services/leaderboard.ts#L43), [порядок записи и ответа](apps/server/src/routes/runs.ts#L43), [схема без идентификатора партии](apps/server/src/db/migrations/001-runs.sql#L7), [повтор на клиенте](apps/web/src/stores/game.ts#L241).

**Воспроизведено.** Два одинаковых POST из R01 возвращают 200; `SELECT count(*) FROM runs` показывает **2**, хотя имя, зал, счёт, волны и версия одинаковы. Группировка рейтинга скрывает повтор визуально, но записи остаются в базе.

**Обычный сценарий ошибки.** Сервер успел выполнить INSERT, а ответ потерялся или клиент получил тайм-аут. «Отправить ещё раз» записывает ту же партию заново. Возможен и отказ уже после INSERT при расчёте места. Намеренный повтор запросов также постепенно раздувает базу: лимит 10 в минуту ограничивает скорость, но не общий объём.

**Последствия.** Лишний расход диска и резервных копий, искажение истории партий и усиление R04. Нельзя обещать надёжную повторную отправку без серверной дедупликации.

**Как исправлять.** Передавать устойчивый `runId`/ключ идемпотентности, сохранять его с UNIQUE-ограничением и привязкой к игроку. Повтор возвращает уже принятый результат; другое тело с тем же ключом отклоняется. Определить срок хранения подробной истории и отдельно хранить лучшие результаты. UNIQUE по пяти нынешним полям не подходит: две разные честные партии могут закончиться одинаково.

**Критерий готовности.** Десять повторов одной партии дают одну запись; повтор после имитации потери ответа безопасен; две разные партии с одинаковым счётом сохраняются согласно политике истории; неподтверждённые ключи не обходят лимиты хранения.

### R04. P2 — запросы рейтинга блокируют API и дорожают с каждой партией

- [ ] Переработать хранение и запросы лучших результатов, проверить задержки под нагрузкой.

**Код:** [ROW_NUMBER по истории](apps/server/src/services/leaderboard.ts#L32), [сортировка до LIMIT](apps/server/src/services/leaderboard.ts#L64), [COUNT DISTINCT и место](apps/server/src/services/leaderboard.ts#L87), [единственный индекс](apps/server/src/db/migrations/001-runs.sql#L25), [DatabaseSync](apps/server/src/db/database.ts#L21).

**Причина.** Для десяти строк топа сначала вычисляются лучшие партии по всем именам, затем сортируется результат. Каждый POST дополнительно ищет лучший счёт имени, количество опережающих и число разных имён. Единственный индекс начинается с `level_id, balance_version`, тогда как основной запрос теперь общий. `LIMIT 10` не ограничивает объём предшествующей работы. Синхронный SQLite выполняет её в том же потоке, который обслуживает HTTP.

**Измерено локально**, в SQLite `:memory:`, с 10 000 разных имён, повторяющимися партиями и общим scope:

| Записей runs | Один `topPlayers(..., 10)` | Один `playerPlace(...)` |
| --- | --- | --- |
| 10 000 | 11 мс | 12 мс |
| 100 000 | 74 мс | 91 мс |
| 500 000 | 412 мс | 483 мс |

Это единичные диагностические замеры на машине разработчика, не прогноз задержек VPS. Время полного GET дополнительно включает `countPlayers`. `EXPLAIN QUERY PLAN` для текущего общего подсчёта игроков показал `SCAN runs` и `USE TEMP B-TREE FOR count(DISTINCT)`.

**Последствия.** Рост задержек всех маршрутов, включая health; несколько клиентов с разрешённой частотой GET могут занять поток API. R03 ускоряет накопление записей. На маленькой текущей базе проблема может быть незаметна — размер production-базы не проверялся.

**Как исправлять.** Поддерживать таблицу лучших результатов транзакционно при записи, индексировать реальные варианты выборок, разделить общий и отфильтрованные SQL, рассмотреть короткий кэш топа. Если подробная история велика, вынести тяжёлые запросы из HTTP-потока. Один дополнительный индекс без замера не считать гарантированным решением.

**Критерий готовности.** Замеры на ожидаемом объёме истории и параллельных запросах укладываются в согласованный бюджет задержки; health остаётся отзывчивым; сохраняются правила равных мест, выбора раннего рекорда и фильтров по залу/версии.

### R08. P2 — клиент считает любое JSON-тело ответа 200 корректным

- [ ] Проверять успешные ответы API во время выполнения перед передачей в store.

**Код:** [приведение as T](apps/web/src/api/leaderboard.ts#L61), [чтение места](apps/web/src/stores/game.ts#L184), [сохранение списка](apps/web/src/stores/game.ts#L263), [обращение к entries.length](apps/web/src/components/LeaderboardTable.vue#L18).

**Воспроизведено.** При подмене `fetch` ответом `new Response('null', { status: 200 })` функция `submitRun` возвращает `{ ok: true, data: null }`. Ответ `{}` для рейтинга проходит через `fetchLeaderboard` как успешный объект. Проверяются JSON-синтаксис и HTTP-статус, но не структура.

**Последствия по коду потребителя.** В первом случае чтение `result.data.rank` бросит исключение вне `requestJson`; вызов через `void submitFinishedRun()` не обрабатывает его. Во втором `entries` становится `undefined`, и шаблон падает на `.length`. Ошибка сервера, несовместимый релиз или неверный прокси превращаются в поломку интерфейса вместо предусмотренного сообщения о недоступности. На нормальном ответе нынешнего Fastify-сериализатора это не проявляется; повреждённый ответ целиком в браузере в рамках ревью не воспроизводился.

**Как исправлять.** Добавить небольшие runtime-проверки ответа отправки и массива рейтинга с проверкой типов/диапазонов обязательных полей; неверные ответы переводить в `unavailable`. Не полагаться на `as T`: приведение исчезает при сборке. Согласовать валидаторы с контрактами, не увеличивая без необходимости клиентский бандл серверной библиотекой схем.

**Критерий готовности.** `null`, `{}`, неверный `entries`, отсутствующие и неверно типизированные поля не вызывают ошибок Vue/unhandled rejection; пользователь видит отказ и может продолжить игру или повторить запрос.

### R09. P2 — Баллиста тратит пробития в порядке массива, а не столкновений

- [ ] Обрабатывать пересечения линейного снаряда в порядке движения по отрезку.

**Код:** [updateLineShot](packages/game/src/systems/combat.ts#L239), [параметры Баллисты](packages/game/src/data/towers.ts#L101).

**Причина.** Для отрезка, пройденного за шаг, код перебирает `state.enemies` и сразу уменьшает `piercesLeft`. Порядок массива соответствует появлению врагов, но после обгонов, замедлений и распада не обязан соответствовать порядку столкновений. При трёх пересечениях за шаг и двух пробитиях один враг пропускается по порядку хранения.

**Воспроизведено на штатном шаге `1/60` с.** Снаряд летит со скоростью 18 от `(0, 0)` вдоль оси X; три одинаковых бунтовщика с HP 1000 стоят в `(0.59, 0)`, `(0.49, 0)`, `(0.39, 0)` и записаны в таком порядке. Радиус попадания бунтовщика с запасом — 0.3, поэтому все три пересекаются с пройденным отрезком `[0, 0.3]`. При уроне 80 и двух пробитиях HP становятся `[920, 920, 1000]`: ближайший враг пропущен. Перестановка массива без изменения геометрии меняет поражённых врагов.

**Последствия.** Урон и результат боя зависят от внутреннего порядка объектов; реальная геометрия полёта не соблюдается. Это отдельная ошибка от ранее отложенного вопроса, должна ли Баллиста изначально выбирать ближайшую цель.

**Как исправлять.** Сначала находить кандидатов и параметр первого пересечения отрезка с окружностью врага, сортировать по этому параметру, затем наносить урон до исчерпания пробитий. Для равных столкновений выбрать детерминированное правило. Простая сортировка по расстоянию до центра менее точна при разных радиусах.

**Критерий готовности.** Перестановка массива не меняет попадания при неизменной геометрии; ближайшие пересечения обрабатываются первыми; есть проверки разных радиусов и уже поражённых целей. После изменения повторить балансные замеры и решить вопрос обновления `BALANCE_VERSION`.

### R10. P2 — известная DoS-уязвимость minimatch в инструментах разработки

- [ ] Обновить совместимую цепочку ESLint/typescript-eslint и lock-файл; добавить регулярную проверку advisories.

**Код:** [minimatch 10.2.6 в lock-файле](package-lock.json#L2842), [devDependencies](package.json), [CI-проверки](.github/workflows/check.yml).

**Подтверждение.** `npm audit --json` сообщает `GHSA-g3hv-75wg-m249` / `CVE-2026-118764` и диапазон `>= 7.0.0, < 11.0.1`. [Advisory проекта minimatch](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249) прямо подтверждает проблему в установленной здесь версии `10.2.6`: разрастание glob-шаблона при `optimizationLevel >= 2`; исправление — `11.0.1`.

**Граница риска.** Девять moderate в отчёте — `minimatch` и восемь зависимых пакетов ESLint/typescript-eslint, а не девять независимых первопричин. Это инструменты разработки; production-audit чист. Доступ посетителя игры к уязвимому glob-пути не найден. Практическая эксплуатация зависит от того, получает ли инструмент недоверенный шаблон с нужными настройками; такой путь в текущем CI не доказан. Возможные последствия — расход CPU/памяти и отказ сборки/линтера.

**Как исправлять.** Подобрать совместимые версии зависимых пакетов, проверить ограничения Node/TypeScript/ESLint и обновить lock-файл. Не запускать вслепую `npm audit fix --force`: текущий отчёт, например, предлагает для `typescript-eslint` версию `8.36.0` при установленной `8.72.2`, что не является проверенным планом обновления. Проверять advisories по расписанию или при обновлениях зависимостей: обычный `npm run check` не является security-audit.

**Критерий готовности.** Установленное дерево больше не содержит затронутой версии по этому advisory, `npm audit` не сообщает данную цепочку, `npm run check` и e2e проходят после обновления.

### R11. P3 — валидатор уровня пропускает некорректный путь

- [ ] Проверять конечность координат, длину сегментов и общую длину пути до обхода клеток.

**Код:** [проверка только конца пути](packages/game/src/core/level.ts#L35), [создание отрезков](packages/game/src/core/path.ts#L14), [цикл по длине пути](packages/game/src/core/level.ts#L125).

**Воспроизведено.** Для копии существующего уровня с `props: []` вызов `createLevel` принимает `pathPoints: [[4, 4], [4, 4]]` с длиной **0**, а также `[[NaN, 4], [4, 4]]` с длиной **NaN**. Последняя точка внутри поля, поэтому текущая проверка проходит.

**Последствия.** При ошибке в новой карте враги могут мгновенно достигать конца либо никогда не сравняться с длиной `NaN`, из-за чего волна не заканчивается. Промежуточная бесконечная координата также делает длину бесконечной, а цикл разметки клеток потенциально бесконечным; зависание этим примером не запускалось. Нынешние девять встроенных карт таких значений не содержат. Пользовательский ввод карт отсутствует, поэтому это скрытая ошибка валидации, не удалённая уязвимость текущего API.

**Как исправлять.** Проверять каждую координату `Number.isFinite`, требовать положительную конечную длину, явно обработать соседние одинаковые точки. Проверять допустимую геометрию промежуточных точек с учётом разрешённого выхода двери за поле; ограничить работу разметки для чрезмерно длинного пути.

**Критерий готовности.** Нулевая длина, `NaN`, `Infinity` и недопустимые сегменты отклоняются понятной ошибкой до симуляции/разметки; штатные карты продолжают загружаться.

## Текущий план: роли башен

Цель — дать каждой башне сильные и слабые ситуации, не оставляя универсально лучшей башни. Контры мягкие: подходящая башня эффективнее, но не становится единственным ответом.

Роли проверяем по полезному урону на вложенную монету: здоровье врагов обычное, избыточный урон последнего попадания не учитывается. Для ступеней I/II/III берём здоровье волн 1/5/10 и среднее по шести доступным компактным залам. Геометрия отдельного зала может менять порядок башен; отдельные старые регрессии пока используют девять классических карт.

Пять потоков: бунтовщики, лазутчики, латники, огры и плотная толпа бунтовщиков с интервалом 0,2 с. Правила для автоматических проверок:

### Исторические сравнительные критерии v8–v18

Следующие общие рейтинги, отрыв смешанного бота и сравнительная эффективность поддержки относятся к прежним числам и классическим картам; они сохранены отдельной командой `npm run test:balance:legacy`, а не обязательствами текущего баланса v35. Текущие проверки конкретных ролей на компактных картах находятся в `tools/balance/compact-roles.test.ts`; правила механик и согласованные параметры — в `packages/game/test`.

1. На каждой ступени каждая башня прямого урона хотя бы против одного потока входит в первую двойку и хотя бы против одного остаётся за её пределами.
2. Ни одна башня прямого урона не занимает первое место более чем против двух потоков. Ограничение относится к первым местам: пять первых двоек дают десять мест, поэтому ограничить четыре башни двумя попаданиями в двойку невозможно.
3. Лидер потока не превосходит среднее значение более чем в два раза. Более ровные потоки допустимы: искусственно создавать большой разрыв не нужно.
4. В каждом из девяти залов каждая из четырёх моностратегий отбивает как минимум на две волны меньше стратегии «Экономика и поддержка». Считаем отбитые волны (`wavesCleared`), а не номер волны поражения; зависшая волна — ошибка.

Правила 1–3 относятся к прямому урону (Лучник, Огневик, Баллиста, Пушкарь). Для поддержки (Морозко, Ловчий, Колдун, Звонарь, Казна) личный урон не измеряет ценность роли: их проверять по вкладу в смешанную стратегию и эффекту на союзников.

Поддержка сравнивается с дополнительными атакующими башнями за тот же доступный бюджет в подходящем сценарии. Для одиночной Казны проверяются общая и дополнительная окупаемость каждой ступени (6–7 волн, без продажи); для соседних Казён — бонус и округление выплат. Средства стратегии к десятой волне проверяются отдельно. Бот разводит огонь с холодом и сетями, а между волнами ждёт готовности башен; старый выбор клеток по одному покрытию сохранён для сравнения.

С v9 проклятие Колдуна I/II/III также снижает получаемое лечение на 35/50/65%. Важен статус получателя: проклятый знахарь полностью лечит непроклятых соседей. Проклятия не складываются, действует сильнейшее; после окончания лечение снова полное. Это мягкая контра знахарям, без полного запрета лечения. Проверяются все ступени, окончание эффекта, взаимное лечение знахарей и группы с их числом и здоровьем для волн 30/34/35.

`npm run towers` показывает три разных замера: роли на живых врагах; предельный урон по бессмертным мишеням; армии за общий бюджет 420 на волнах 1/10/20 с числом убийств, пропусков и потерянных жизней. Предельный урон сам по себе не доказывает, что башня лучше против мелких врагов.

## Устройство проекта

- `packages/game` — правила, данные баланса и уровни; чистый TypeScript без интерфейса и браузерных API.
- `apps/web` — Vue-интерфейс, Canvas-отрисовка, звук и клиент API.
- `apps/server` — Fastify API и SQLite.
- `packages/contracts` — общие схемы и типы API.
- `tools/balance` — измерения башен, симуляции ботов и проверки баланса.
- `deploy` и `.github/workflows` — конфигурация и автоматическая выкладка; изменения в `main` деплоятся на сервер.

## Рабочие правила

- Ветки не сливать без отдельной команды владельца. Слияние v9 в `main` и выпуск сделаны по прямой команде 16 ноября; состояние веток после выпуска записано в «Текущем состоянии».
- При изменении чисел игры обновлять `BALANCE_VERSION` в `packages/game/src/data/balance.ts`.
- Для баланса запускать `npm run towers`, `npm run balance` и `npm test`; для интерфейсных изменений — `npm run e2e`. Перед слиянием — `npm run check`.
- Логика игры остаётся детерминированной и независимой от Vue, DOM и Node. Схемы запросов и ответов API менять согласованно в `packages/contracts`, клиенте и сервере.
- Секреты не коммитить. Изменения выкладки вносить через файлы `deploy/`.

## Команды

```bash
npm run dev          # веб-приложение
npm run dev:server   # API
npm run towers       # сравнение эффективности башен
npm run balance      # симуляция стратегий по залам
npm test             # тесты
npm run e2e          # проверка в Chrome
npm run check        # форматирование, линтер, типы, тесты и сборка
```
